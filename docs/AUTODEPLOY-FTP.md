# Автодеплой на хостинг по FTP

Сайт собирается в GitHub Actions и сам заливается на хостинг по FTP.
Сейчас хостинг — **Cloud4box** (панель ISPmanager, каталог сайта `public_html`).
Каждый push в `main` → новый сайт на хостинге. Вручную загружать архив больше не нужно.

```
push в main  →  сборка release/php  →  проверки  →  загрузка в public_html  →  готово
```

На хостинге по-прежнему нужен только PHP 8 и Apache — Node.js там не нужен,
вся сборка идёт на стороне GitHub.

---

## Что нужно сделать один раз

### Шаг 1. Узнать данные FTP

Панель Cloud4box (ISPmanager). Данные FTP лежат в разделе **«FTP-учётные записи»**
(может называться «FTP-аккаунты» / «Пользователи FTP»). Запишите четыре значения:

| Что | Пример | Где взять |
|---|---|---|
| хост | `ваш-домен.ru` или `12.34.56.78` | в ISPmanager FTP-хост — это домен сайта или IP сервера |
| логин | `cloud4box_login` | колонка «Имя» / «Логин» |
| пароль | `••••••` | если не помните — нажмите «Изменить» и задайте новый |
| каталог (директория) | `public_html` | корень сайта; если `public_html` — ссылка, укажите `www/ваш-домен.ru` |

Эти же четыре значения идут в GitHub: `FTP_HOST`, `FTP_USER`, `FTP_PASSWORD`, `FTP_DIR`.
Если хостинг когда-нибудь сменится, меняются только они.

Если панель предлагает «FTPS / FTP over TLS» и без него не пускает — добавьте
`FTP_SECURE` = `1`, это шифрует пароль при передаче. В остальных случаях ничего
добавлять не нужно.

### Шаг 2. Выбрать ветку автодеплоя

Автодеплой срабатывает на push в ветки, перечисленные в `.github/workflows/deploy.yml`.
Сейчас это `main` и рабочая ветка `arena/46865502-sait`. Укажите в списке только
ту ветку, которую хотите автоматически публиковать.

### Шаг 3. Добавить секреты в GitHub

Репозиторий → **Settings → Secrets and variables → Actions → «New repository secret»**.
Нужны **четыре** секрета — ровно то, что показывает панель хостинга:

| Имя секрета | Значение |
|---|---|
| `FTP_HOST` | хост FTP: ваш домен или IP сервера |
| `FTP_USER` | логин FTP |
| `FTP_PASSWORD` | пароль FTP |
| `FTP_DIR` | корень сайта из ISPmanager; абсолютный (`/www/cosmorox.ru`) или относительно FTP-входа (`public_html`). Значение `/` означает домашний каталог FTP-аккаунта — выбирайте его, если домен фактически открывает файлы именно оттуда |

Начальный `/` сохраняется: он не преобразуется в путь относительно домашней папки FTP-пользователя.

Этих четырёх секретов достаточно. Необязательный `SITE_URL` переопределяет адрес
проверки после FTP-загрузки; по умолчанию workflow проверяет `https://cosmorox.ru/`
и требует HTTP 200, затем проверяет маркер новой версии в выданном `app.js`.

`FTP_PORT` и `FTP_SECURE` добавлять не нужно: обычный FTP работает по умолчанию,
порт 21 подставляется сам. Секрет нужен, только если хостинг требует FTPS —
тогда добавьте `FTP_SECURE` = `1`.

Пароль хранится только в секретах GitHub: он не попадает ни в репозиторий,
ни в логи, ни в файлы сайта.

### Шаг 4. Первый запуск (проверка)

Actions → workflow **«Деплой на хостинг (FTP)»** → **«Run workflow»** →
ветка `main` → **Run**.

Первый запуск делайте в быстром режиме (галочка «Залить готовый архив» включена
по умолчанию): он берёт уже собранный `download/astra-pearl-php.zip`, не собирает
сайт заново и укладывается в одну-две минуты. Полный режим (снять галочку) —
это сборка из исходников + типы + 107 тестов + 277 проверок админки, около 5 минут.

Залить сайт из рабочей ветки, не вливая её в `main`: в окне запуска выберите
ветку в списке «Use workflow from».

Через 3–5 минут в логе будет отчёт:

```
· подключение к ваш-домен.ru:21
· каталог сайта: public_html
· загружено: 84, без изменений: 0, удалено: 0
· готово: откройте сайт и проверьте страницы и вход в кабинет
```

Откройте сайт. Если он открылся — автодеплой настроен, дальше всё происходит само
при каждом push в `main`.

## Что деплой НЕ трогает

Это главное в автодеплое: обновление сайта не должно ломать настройки и терять заявки.

| Файл на сервере | Почему не трогаем |
|---|---|
| `config.php` | пароль владельца, почта, Telegram, название сайта |
| `data/` | заявки, сессии, счётчики лимитов |
| `setup.php` | если он ещё есть — установка не пройдена; если удалён — деплой не вернёт его обратно |

Эти правила зашиты в `scripts/deploy-ftp.ts` и проверяются тестом
`tools/php-checks/deploy-ftp.cjs` (15 проверок на локальном FTP-сервере).

## Как workflow убеждается, что сайт обновился

После FTP-загрузки запускается шаг **«Проверка публикации на домене»** — он
ловит две частые проблемы, при которых «деплой прошёл», а сайт остался старым.

**1. Зонд деплоя.** Скрипт кладёт на хостинг маленький файл
`deploy-probe-<коммит>.txt`. Workflow открывает его по HTTP на домене. Если
зонда нет — файлы загрузились мимо корня документов: неверный `FTP_DIR`
или домен смотрит на другой сервер. Никакая правка кода это не чинит,
менять нужно секрет `FTP_DIR` (или привязку домена в панели).

**2. Версии статики с отпечатком.** Сборка кладёт главные бандлы под именем
с отпечатком сборки: `app-e616bd1c.js`, `styles-e616bd1c.css` — имя меняется
с каждым билдом. Страницы ссылаются на новое имя, поэтому кэш хостинга и
браузера физически не может отдать прежний скрипт. Обычные `app.js` и
`styles.css` остаются в сборке для совместимости (на них смотрят `check.php`
и кабинет). Деплой сам удаляет с сервера бандлы прошлых сборок и зонды
прежних запусков.

Проверка работает в обоих режимах: и в полном (сборка из исходников), и в
быстром (готовый архив из `download/`). Если проверка не прошла — запуск
покраснеет, а в логе будет точная причина: что ожидалось и что увидели.

## Деплой со своего компьютера

Тот же скрипт можно запускать вручную — например, чтобы залить сайт, не дожидаясь GitHub.

```bash
cp .env.deploy.example .env.deploy   # один раз
# откройте .env.deploy и впишите FTP_HOST, FTP_USER, FTP_PASSWORD, FTP_DIR
npm run deploy:ftp
```

`.env.deploy` в git не попадает (он в `.gitignore`), поэтому пароль остаётся у вас.

Полезные режимы:

```bash
npm run deploy:ftp -- --dry-run    # показать, что будет загружено, ничего не меняя
npm run deploy:ftp -- --no-build   # залить уже собранный release/php
npm run deploy:ftp -- --prune      # удалить на сервере файлы, которых нет в сборке
```

По умолчанию `--prune` не включён: скрипт только предупреждает о «лишних» файлах,
ничего не удаляя. Удаление включайте галочкой при ручном запуске workflow
или флагом `--prune` — например, после переименования страницы.

## Если что-то пошло не так

| Симптом в логе Actions | Причина и решение |
|---|---|
| `530 Login incorrect` | неверный логин/пароль в секретах; перевыпустите пароль FTP в панели и обновите `FTP_PASSWORD` |
| `ECONNREFUSED` / `ETIMEDOUT` | неверный `FTP_HOST` или хостинг блокирует FTP с зарубежных адресов — включите FTPS (`FTP_SECURE=1`) или деплойте с компьютера |
| `550 Permission denied` | FTP-пользователь не имеет прав на папку, либо неверен `FTP_DIR` (проверьте путь в панели: `public_html` или `www/ваш-домен.ru`) |
| `deploy-probe: HTTP 404` | файлы загружены, но домен их не видит: `FTP_DIR` — не корень документов домена (например, загрузка ушла в `public_html`, а домен привязан к `/www/cosmorox.ru`), либо домен привязан к другому серверу. Следом запускается шаг «Диагностика каталогов FTP» — в его логе видна структура каталогов сервера; найдите там корень домена из панели («Сайты») и впишите этот путь в секрет `FTP_DIR` |
| `deploy-probe-home: HTTP 200`, а зонд из `FTP_DIR` — нет | домен обслуживает **домашний каталог FTP-аккаунта**, а не каталог из панели (панель может показывать что угодно — веб-серверу виднее). Впишите в секрет `FTP_DIR` значение `/` (один слэш) и запустите деплой снова |
| «Домен отдаёт прежнюю версию страницы» | HTML на сервере остался старым: чаще всего неверный `FTP_DIR` (см. строку выше) или кэширование страниц в панели — сбросьте кэш хостинга |
| предупреждение про SITE CHMOD | FTP не даёт менять права — выставьте в панели: папки 755, файлы 644, `data/` — 775 |
| `не заданы: FTP_HOST (хост), …` | секрет не добавлен или добавлен с другим именем (регистр важен — скрипт сам скажет, чего не хватает) |
| Сайт открылся, но нет стилей | ранее архив распаковали в подпапку; с `--prune` лишняя папка удалится, а файлы встанут в корень |
| В логе «на сервере N файлов, которых нет в сборке» | это старые файлы от прошлых загрузок; проверьте список и запустите с `--prune` |

### Проверки перед загрузкой

Workflow не заливает сайт, если что-то сломано: `tsc`, тесты (107), проверки
админки (277), статической версии (93) и самого деплоя (15). Так на хостинг
не попадёт сборка с ошибкой.

## Откат

Автодеплой перезаписывает файлы сайта, но не базу заявок.

1. В GitHub откройте коммит, который был до сломанного.
2. `Actions → Деплой на хостинг (FTP) → Run workflow` — но он соберёт текущий код.
   Поэтому надёжнее: `git revert <плохой коммит>` → push в `main` → деплой сам вернёт прошлую версию.
3. Заявки и `config.php` при откате не пострадают.

## Смотреть, что загрузилось

Каждый запуск оставляет итог в **Actions → нужный запуск → Summary**:
ветка, коммит, количество загруженных файлов. Историю деплоев видно там же.
